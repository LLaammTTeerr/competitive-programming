# Problem-setting pipeline — design

Five new skills that take a problem from an idea to a Polygon-ready package:
constraint and subtask design, testlib generators/validator/checker, a zoo of
deliberately-wrong solutions used to measure test strength, an end-to-end
review, and an umbrella that sequences them.

Status: **design approved, not implemented.**

---

## 1. Why

`competitive-programming` today covers the contestant side (`solving-problems`,
`running-contests`) plus one setter-side skill (`writing-statements`). A
statement alone is not a problem: it needs tests that are legal and strong, a
checker, a model solution, and evidence that all of them agree. Today that work
is unautomated and its quality is unmeasured.

The pipeline is judged on one thing: **when it says a package is ready, there is
machine-readable evidence for the claim** — not an assertion that it looks fine.

## 2. Decisions

| Decision | Choice |
|---|---|
| Target judge | Polygon |
| Deliverable | Polygon-shaped working directory + local runner. No `problem.xml` — Polygon writes that. |
| Plugin | One. `competitive-programming`, bumped to 0.5.0. Not a second plugin. |
| New skills | 5: `shaping-problems`, `preparing-tests`, `validating-solutions`, `reviewing-problems`, `creating-problems` |
| testlib | `qhhoj/testlib`, cloned to a cache and read from `docs/usage-guide.md`; never paraphrased into a skill |
| Metadata | JSON, always generated, never hand-typed |
| Human in the loop | One blocking gate (idea, story, subtasks) plus one exceptional stop |
| Scope | Batch problems only. MLE adversaries in. Interactive, editorial, English statement deferred. |

### Rejected, with reasons

- **A second plugin for the setter side.** Splitting does nothing for routing —
  the model sees one flat list of descriptions from every installed plugin, so
  the namespace helps a human typing `/` and not the router. Meanwhile
  `creating-problems` delegates to `solving-problems`, which becomes a
  cross-repo runtime dependency that fails as `Unknown skill`. Revisit past ~10
  skills, or if the setter half is ever handed to someone who does not compete.
- **A skill for developing vague problem ideas.** That is
  `superpowers:brainstorming`. `shaping-problems` delegates the dialogue to it
  and owns only the CP-specific judgement.
- **Forking the package on an unresolvable ambiguity** (building both readings
  in parallel). Roughly doubles the run and leaves a confusing directory; the
  case is rare enough to be worth a stop.
- **A gate at every phase boundary.** Most stops would be on decisions approved
  unread. Replaced by the flag register (§6).

## 3. Skill set

```
competitive-programming/skills/
  solving-problems      exists   contestant side; also writes the model solution
  running-contests      exists   contestant side
  writing-statements    exists   Vietnamese statement prose via vnolymp
  shaping-problems      NEW      idea -> spec: originality, difficulty, N, subtask ladder
  preparing-tests       NEW      validator, checker, generators, sample selection
  validating-solutions  NEW      the zoo, the invocation matrix, the arbiter
  reviewing-problems    NEW      end-to-end audit, standalone or invoked
  creating-problems     NEW      umbrella; owns the gates and the loop-back edges
```

### Disambiguation is a runtime behaviour, not a description

Routing happens before a skill loads, so a description cannot ask a question.
Every new skill therefore opens with:

```markdown
## Am I the right skill?

If the request plausibly means one of these instead, **ask before doing
anything** — one question, options being each neighbour and "both, in this
order".

| If it's really about | Use |
|---|---|
| ... | competitive-programming:... |

Ask only when genuinely ambiguous. "Write me a validator" is not ambiguous.
"Make my tests better" is.
```

Three known collision zones, and how each description resolves them:

| Zone | Collides on | Discriminator |
|---|---|---|
| `preparing-tests` ↔ `validating-solutions` | "test my problem" | *builds test data* (`generator`, `validator`, `checker`, `testlib`) vs *attacks with solutions* (`wrong solution`, `stress`, `is my suite strong`) |
| `shaping-problems` ↔ `brainstorming` ↔ `writing-statements` | "help me design a problem" | shaping owns **numbers** (N, ladder, difficulty); statements owns **prose**; brainstorming is delegated to, never competed with |
| `reviewing-problems` ↔ `/code-review` | "review this" | a **problem package** (statement, tests, proofs) vs a **diff** |

For most collisions "both" already has a name: `creating-problems`, which
exists to sequence the others.

## 4. The problem directory

```
<problem>/
  problem.json          written by the skill at Gate 1; authoritative thereafter
  solutions.json        GENERATED by scanning solution header comments
  invocation.json       GENERATED by each pipeline run
  flags.json            GENERATED; accumulates across the run
  files/
    constraints.h       GENERATED from problem.json
    validator.cpp  check.cpp  gen-*.cpp
  solutions/
    sol-main.cpp  sol-*.cpp
  tests/
  statements/vietnamese/<problem>.tex
  tests-script.txt      Polygon syntax; paste into the Polygon UI
  run-pipeline.sh       local build + invoke, for the cross-check
```

### The consumer problem

Three consumers cannot read JSON: the `.tex`, `validator.cpp`, and every
`gen-*.cpp`. Worse, per `plan.md` **O-09 — "opts are silently generator-only"**
— a validator cannot take bounds on the command line at all;
`registerValidation` exposes only `--testset`, `--group`, `--testCase`. Validator
bounds are therefore always compile-time constants.

Resolution:

- **C++ side** — generate `files/constraints.h` from `problem.json`; the
  validator and every generator include it. One source, compile-time, drift
  impossible by construction.
- **Statement side** — no generation; templating the `.tex` would fight
  vnolymp. A **drift check** compares `problem.json` against the
  `\begin{problem}` key list and the subtask percentages and fails loudly.
- **Reality check** — `validator --testOverviewLogFileName` reports which
  declared bounds the tests actually attain, so `problem.json`'s maxima are
  verified rather than trusted.

### `problem.json`

Written by the skill from Gate 1 decisions. The human never types JSON; changing
it means re-opening Gate 1, not editing the file.

```jsonc
{ "schema": 1, "name": "flight",
  "created": "2026-07-30T13:40:02+07:00",
  "title":  { "vi": "Chuyến bay đầu tiên" },
  "tags":   ["probability", "strings", "automaton"],
  "limits": { "time_ms_published": 1000, "time_ms_computed": 740,
              "memory_mb": 256 },
  "io":     { "input": "stdin", "output": "stdout" },
  "checker":{ "kind": "stock", "name": "rcmp6" },
  "constraints": [ {"id":"len_a","expr":"1 <= |A| <= 20","min":1,"max":20} ],
  "subtasks": [ {"id":"g1","points":40,"constraints":["|A| <= 6","|B| <= 6"]},
                {"id":"g2","points":60,"constraints":[],"depends_on":["g1"]} ],
  "examples": [ {"test":"sample-01","note":"A thắng dứt điểm"} ] }
```

`tags` are **topic** tags. Polygon **solution** tags live in `solutions.json`.
`examples` holds test references and a one-line note; the Vietnamese
`\Explanation` prose stays in the `.tex`, because `writing-statements` owns
prose and two writers of Vietnamese is one too many.

### Solution metadata lives in the source

Metadata beside the code cannot desynchronize from it, and renaming a file does
not orphan it. `solutions.json` is a scan product, regenerated every run.

```cpp
/**
 * @tag        wrong-answer
 * @expect     g1=WA g2=WA
 * @algorithm  Compares first occurrence by START index rather than END index.
 * @why-wrong  Diverges from the model exactly when |A| != |B|.
 * @complexity O(|A| + |B|)
 */
```

**Timestamps are derived, never written.** `git log -1 --format=%cI <file>`
when the directory is a repo, `stat` mtime otherwise. A timestamp a human
maintains is a timestamp that lies.

**Timestamp only what changes.** `generated_at` in every file means every run
produces a git diff even when nothing moved, which trains you to stop reading
diffs. It belongs in `invocation.json` and `flags.json`; everything else derives.

### `invocation.json`

Generated, never hand-edited, and committed — it is the evidence.

```jsonc
{ "schema": 1, "generated_at": "...",
  "machine": {"cxx":"g++ 13.2","flags":"-O2 -std=c++17"},
  "t_main_ms": {"per_test": {...}, "max": 370, "runs": 3, "method": "median"},
  "limits": {"tl_ms": 1000, "kill_ms": 2000},
  "results": [ {"solution":"sol-brute.cpp","group":"g2","test":"07",
                "verdict":"TL","time_ms":2000,"ratio":">=5.4","killed":true} ],
  "holes":   [ {"solution":"sol-greedy-startpos.cpp","group":"g1",
                "expected":"WA","actual":"OK"} ] }
```

`holes` **is** the strength report. A hole is a solution the suite failed to
kill where its manifest said it should. `holes: []` is the only definition of
"strong" that is not circular.

### Per-group expectations, not one verdict

A solution can legitimately be `OK` on subtask 1 and `TL` on subtask 2, and
Polygon's single global tag cannot express that. `@expect g1=OK g2=TL` can, and
it makes strength mechanically checkable: **every `WA` and `TL` cell must be
realized by at least one test in that group.**

## 5. Timing

Never wall-clock against a constant. Everything is a ratio to the model
solution, measured on one machine with one set of flags, recorded in
`invocation.json` so the numbers stay interpretable later.

```
t_main   = max over tests of (median of 3 runs)
TL       = max(2 × t_main, 1000 ms), rounded up to a human number
kill at  = 2 × TL   (= 4 × t_main when the floor is not binding)
verdict  = AC if t <= TL, else TLE
band     = (TL, 2×TL] — strictly over TL (t == TL is still AC), up through
           2×TL: finished but over: FLAG, never claim a verdict
```

Rationale for each part:

- **The floor.** With `t_main` at 8 ms, `TL = 16 ms` is nonsense — process
  startup is ~2 ms and scheduler noise dominates. Default 1000 ms, overridable
  in `problem.json`.
- **Median of 3.** Single-run timing swings 20–50% on turbo, cache state and
  background load, and one noisy `t_main` poisons every downstream verdict
  because everything is a ratio to it.
- **Max, not mean.** The limit must hold on the worst test.
- **Published vs computed.** The `.tex` says `time = 1`; if the formula yields
  0.74 s, publish 1 s and record both.

**Accepted trade-off:** killing at `2×TL` means the report can never distinguish
"3× too slow" from "1000× too slow" — it can only say `>= 2×TL`. That is the
right trade for pipeline speed, and the band flag is what keeps it honest. A
solution sitting at 2.01×TL locally is a coin flip on the judge's hardware, and
gets reclassified to `time-limit-exceeded-or-accepted` automatically.

MLE uses the same shape on peak RSS.

## 6. Gates and the flag register

**One blocking gate: G1 — idea, story, subtasks.** It is the input, it is
creative, and it produces `problem.json`.

Everything else **flags and continues**. Flags are emitted inline the moment
they happen — so an interruption is possible in real time — and accumulate in
`flags.json`:

```jsonc
{ "id": "amb-001", "phase": "prepare-tests", "severity": "high",
  "kind": "statement-ambiguity",
  "what": "\"xâu con\" reads as substring or as subsequence",
  "assumed": "substring (contiguous)",
  "changes_if_wrong": "sol-main, gen-boundary, 3 tests in g1",
  "at": "2026-07-30T14:02:11+07:00" }
```

`changes_if_wrong` is what makes flag-don't-stop safe rather than reckless: it
prices the interruption before you decide to make one. Severity is `high` when
the decision changes the problem, `medium` when it changes only the tests, `low`
for cosmetic.

Flagged, not gated: algorithm choice, borderline TLE reclassification, checker
stock-vs-custom, sample selection, every reviewer judgement call.

### The one exception

An unresolvable **HIGH statement ambiguity** stops the pipeline. It is the only
case where continuing invalidates the entire package rather than one phase, so
the cost of a wrong guess exceeds the cost of waiting.

`flags.json` was added after the three-file split was agreed; it is generated
like the others. It is separate from `invocation.json` because flags arise in
every phase, including shaping and statement writing, while invocation results
arise in exactly one.

## 7. The pipeline

```
  writing-statements ──> statement, NO \Examples yet
           │              constraint table = single source of truth
           v
  solving-problems  ──> sol-main.cpp                        [main]
           │
           v
  preparing-tests   ──> check.cpp / stock checker    FIRST
                    ──> validator.cpp                SECOND
                    ──> gen-*.cpp                    THIRD
                    ──> tests, grouped to subtasks
           │
           v
  validating-solutions ──> the zoo, each with @tag and @expect
                       ──> invocation matrix: every solution × every group
           │
           ├─ rejected solution SURVIVED ────> suite too weak ─> back to generators
           ├─ accepted solutions DISAGREE ───> arbiter ─> back to sol-main
           │                                     └─ or ─> STOP: statement ambiguity
           └─ every expectation met ──> pick 2–3 tiny tests
                                        └─> back to writing-statements for
                                            \Examples + \Explanation
```

Three properties of this ordering that a naive statement→tests→solutions flow
gets wrong:

1. **The statement cannot finish first.** `writing-statements` refuses to author
   samples; samples come from the generator and the model solution. So the
   statement starts without `\Examples` and the pipeline returns to it.
2. **Checker and validator precede the generators.** Otherwise you generate a
   thousand tests and learn afterwards they violate a bound. The checker is
   first because "do these two solutions agree?" is meaningless without one
   whenever several outputs are valid.
3. **The disagreement loop needs an arbiter**, and a third exit (§10).

**Resumability.** State lives entirely in files on disk; every phase is
idempotent; re-entering picks up where it stopped. A pipeline that cannot
restart after an interruption is one nobody interrupts, which defeats the flag
register.

## 8. `shaping-problems`

Owns what nothing else does: **is this already a known problem, what difficulty
is intended, what N separates the intended solution from the naive one, and what
subtask ladder pays for real partial insight** rather than for typing.

**Invokes:** `brainstorming`.

**Terminal-state override, stated explicitly in the SKILL.md.** `brainstorming`
hard-gates on presenting a design and prescribes exactly one terminal action —
invoke `writing-plans`, and no other skill. Here the terminal state is a
completed `problem.json` handed to `creating-problems`. Without the override the
two fight.

## 9. `preparing-tests`

**Mission: legal, reaching, answerable.**

1. Read `problem.json`; emit `files/constraints.h`; drift-check the `.tex`.
2. **Checker.** Unique answer → a stock checker from the 21 in `checkers/`
   (`ncmp`, `wcmp`, `rcmp6`, `yesno`, `lcmp`). Otherwise custom. Never write a
   custom checker when a stock one does: a mis-parse of `ans` in a custom
   checker surfaces as `_fail`, i.e. it breaks the problem rather than a
   submission.
3. **Validator**, before any generator exists. `registerValidation(argc, argv)`
   always — the bare form silently disables `--group`. Name every variable
   (`readInt(1, 20, "n")`) so bounds analysis works. Branch on
   `validator.group()`. Enforce format strictly: `readSpace`, `readEoln`,
   `readEof`.
4. **Generators.** `registerGen(argc, argv, 2)` always — version 1 repeats
   `rnd.next(0,1)` every 65536 draws (R-01/R-02), quietly ruining a large random
   test. `opt<bool>("f", false)`, never `has_opt` (O-02). Pure functions of the
   command line. Five families: random, max-size, boundary/degenerate,
   structured-adversarial, hand-written.
5. Tests script in Polygon syntax, grouped; validate every test under its own
   `--group`.
6. **Reaching check** — `--testOverviewLogFileName` per group; any declared
   bound no test attains is a hole.
7. **Samples last.** 2–3, small enough to trace by hand, chosen to exercise the
   interesting rule rather than the trivial path, and produced by the model
   solution and checker like every other test. Never hand-computed.

**Done means:** every test validates under its own `--group`, and every declared
bound is reached by some test.

**Invokes:** `test-driven-development` (the validator and checker have testable
behaviour — feed the validator a deliberately-illegal input and assert nonzero
*before* writing generators; almost no package does this),
`dispatching-parallel-agents`, `verification-before-completion`.

## 10. `validating-solutions`

**Mission: attack.**

| Class | Job |
|---|---|
| `accepted`, alternative algorithm | cross-check oracle — worth nothing unless genuinely independent, not a transcription |
| `accepted`, exhaustive, tiny-N | **the arbiter.** Exists to break ties, not to pass the suite |
| `wrong-answer`, plausible greedy | what a contestant actually submits |
| `wrong-answer`, boundary | dies on n=1, all-equal, degenerate |
| `wrong-answer`, overflow | `int` where `long long` is needed — kills any suite that never reaches the value bound |
| `wrong-answer`, misread statement | e.g. start- vs end-position on `flight` |
| `time-limit-exceeded` | correct, wrong complexity class |
| `time-limit-exceeded-or-accepted` | the honest home for borderline |
| `memory-limit-exceeded` | correct, allocates too much |

Two rules make the zoo worth writing:

- **Each wrong solution is wrong in exactly one named way.** One wrong in three
  ways proves nothing about which test caught it.
- **Wrong solutions must be plausible, not strawmen.** The bar is "would a
  competent contestant submit this at 2am?" A greedy nobody would write catches
  nothing and inflates the report.

### Strength, defined without circularity

Three independent obligations:

- **Adversarial** — every rejected solution fails, and the report names the test
  that killed it. The claim is always *"no solution in the zoo survives"*, never
  *"the tests are strong"*.
- **Reaching** — every declared bound is attained by some test in its group.
- **Structural** — a per-shape checklist: min and max sizes, all-equal,
  all-distinct, value extremes, degenerate structures (star / path / caterpillar
  for trees), anti-hash and anti-quicksort where the model invites them.

### The arbiter

1. Two `accepted`-class solutions disagree on input X.
2. Shrink X to minimal.
3. Run the tiny-N exhaustive brute. Whichever it agrees with is right.
4. If it cannot decide — or cannot be written, because the behaviour genuinely
   is not defined anywhere — that is **statement ambiguity**, and the pipeline
   **stops**. Never silently pick a side.
5. Hard stop after 3 rounds regardless, with the minimal case.

**Done means:** `holes` is empty, and every `WA`/`TL` cell names the test that
realized it.

**Invokes:** `dispatching-parallel-agents` (N wrong solutions, zero shared
state — the strongest fit in the design), `systematic-debugging` (the arbiter
loop is a debugging loop; its core rule, understand before proposing a fix, is
exactly the failure mode of guessing which solution is wrong),
`verification-before-completion`.

## 11. `reviewing-problems`

Runs as a **subagent with fresh context**, not inline. A reviewer that inherited
the assumptions of the agent that wrote the statement cannot see the assumed
definition.

Checklist:

- **Statement ambiguity** — any sentence with two readings.
- **Assumed definitions** — a term used as though the reader already knows it.
  Live example: the `flight` statement written on 2026-07-30 says `xâu con`,
  which reads as *substring* to most Vietnamese contestants and *subsequence* to
  some; the unambiguous form is `xâu con liên tiếp`. It is not fatal there — the
  body defines occurrence precisely via `t_A` — but it survived a verification
  pass and would have shipped.
- **Unproven solution steps** — a header comment claiming an invariant with no
  argument behind it.
- **Constraint drift** — `problem.json` vs `.tex` vs `constraints.h`.
- **Unreached bounds**, **matrix holes**, **checker/validator disagreement with
  the stated format**.

Mechanical findings it fixes and re-runs. Judgement calls it flags.

**Invokes:** `requesting-code-review`, `verification-before-completion`.

## 12. `creating-problems`

Two entry modes, detected at G1: a finished idea and algorithm → prepare exactly
that; a half-idea → delegate to `shaping-problems`.

Sequences the phases as subagents, owns the gates and the loop-back edges, and
consumes reviewer findings.

**Invokes:** `subagent-driven-development`, `receiving-code-review`,
`writing-plans` (conditionally, when a problem needs more than the standard
pipeline).

`receiving-code-review` is load-bearing here, not decorative. A reviewer
subagent will produce some findings that are simply wrong, and in a pipeline
that fixes mechanical findings without asking, a hallucinated constraint
violation would otherwise get a correct validator "fixed" into a broken one.

## 13. testlib

Same pattern `writing-statements` uses for vnolymp: clone `qhhoj/testlib`
shallow into `${XDG_CACHE_HOME:-$HOME/.cache}/testlib` with the clone-aside-then-
`mv -T` race guard, then read `docs/usage-guide.md` for the API and `plan.md`
for known defects.

**No testlib API is copied into a skill file.** The guide is 902 lines and
versioned against the header being compiled; a paraphrase goes stale the moment
a bug is fixed. The skills carry only what the guide does not: subtask binding,
strength doctrine, the cross-check loop.

The ~12-line bootstrap is duplicated in each skill rather than hoisted into a
shared reference — a cross-skill path is fragile, and `writing-statements`
already duplicates its own.

```sh
g++ -std=c++17 -O2 -Wpedantic -Werror -I"$TESTLIB" file.cpp -o file
```

Never `-ffast-math`: testlib detects it at runtime and aborts.

Traps to encode, all from the fork's own audit:

- `registerGen(argc, argv, 2)`, never 0 or 1 (R-01, R-02)
- `registerValidation(argc, argv)`, never bare
- `opt<bool>("f", false)`, never `has_opt` (O-02)
- opts are generator-only (O-09) — validator bounds are compile-time
- a read failure on `inf`/`ans` is promoted to `_fail`, never `_wa`
- there is no `registerChecker`; checkers use `registerTestlibCmd`
- checkers must never `assert` — use `quitf(_fail, …)`

## 14. Verification

Three levels, because "the skill exists" is not evidence.

- **Authoring** — `superpowers:writing-skills` for all five.
- **Routing** — `skill-creator` trigger evals across all eight descriptions,
  turning the collision worry into a number.
- **End-to-end** — **`flight` is the fixture.** It already has a statement, and
  it contains three things the pipeline must catch: a float answer forcing the
  `rcmp6`-vs-custom decision, a start-vs-end-position confusion that is a
  natural `wrong-answer` solution, and the `xâu con` assumed definition the
  reviewer should flag. If a run on `flight` does not surface all three, the
  skills do not work.

## 15. Out of scope

Deferred, none of which forces a redesign later:

- **Interactive problems** — need an interactor, a cross-runner to wire two
  processes' pipes, and a different cross-check model. The testlib checkout
  notes there is no JRE on this machine for its own interactor tests.
- **Editorials** from the alternative correct solutions, into vnolymp's
  `tutorial` environment.
- **English statements** alongside Vietnamese.
- **A Polygon export tree** (`problem.xml` plus pre-generated tests).
